## 수정 우선순위

### R1 · High · 카드 후보가 없으면 런이 영구 정지한다

- 위치: `src/game/simulation/round-resolution-system.ts`의 `offerCards`, `src/game/application/commands/card-commands.ts`의 `tickCardSelection`.
- 원인: 규칙 카드는 6종이고 선택 후 제거된다. 아이템을 장착할 실험체가 없으면 아이템도 모두 제외한다. 후보 수를 검사하지 않고 `card-selection`으로 전환하고, 시간 초과 시 첫 카드가 없으면 그대로 반환한다. 이 단계에서는 복제·폐기도 막혀 있어 복구할 수 없다.
- 최소 재현: 초기 run을 바탕으로 `phase='combat'`, `round.number=35`, `units=[]`, `activeRuleEffects=[...ruleCards]`를 설정해 `offerCards` 호출 후 `tickCardSelection(state, 21, context)` 실행. 실제 결과는 `cardOffer=[]`, `phase='card-selection'`이다. 여섯 번 규칙을 선택한 뒤 35라운드 끝 직전에 남은 실험체를 폐기하는 경계 상황에 해당한다. 이 상태는 함수 수준으로 재현했으며 전체 플레이 경로는 미실행이다.
- 후보 부족도 존재: 규칙 4종을 선택하고 남은 실험체 모두가 아이템을 장착했다면 다음 제시는 2장뿐이다. 예를 들어 5번의 이전 카드 선택을 규칙 4장+아이템 1장으로 구성하고 그 아이템을 가진 실험체 하나만 남긴 경우다.
- 수정 방향: 후보 0/1/2장 정책을 명시한다. 추천은 0장이면 보상 기록 또는 안내를 남기고 다음 준비 단계로 안전하게 진행하고, 1~2장이면 가능한 카드만 제시하는 것이다. 이는 기획의 ‘3장 제시’에 예외를 추가하므로 관련 문서에도 명시한다. 중복 금지·규칙 재등장 금지·장착 불가능 아이템 제외를 몰래 깨지 않는다.
- 완료 조건: 후보 0/1/2/3장 이상 각각의 테스트, 리롤 뒤 고갈 처리, 시간 초과 뒤 정상 진행을 검증한다. 무한 `card-selection`이 없어야 한다.

### R2 · Medium · 기본 밸런스 테스트가 실패하고 기준 보고서가 현재 수치와 다르다

- 위치: `src/test/balance-harness.test.ts:27`, `src/test/balance-harness.test.ts:203`, `src/game/config/provisional-balance.ts:15`, `docs/mvp-balance-report.md`.
- 재현: 환경변수 없이 `npm run test:balance`. 전략 정책 4시드 중 2승(50%), 자동 합성 0승. 211행의 `strategicWinRate <= 0.4`에서 실패한다.
- 원인: 기본 표본은 4개인데 `seeds.length >= 4`부터 15~40% 구간 판정을 적용한다. 4시드 승률은 25% 단위여서 해당 구간을 통과하는 결과는 정확히 1승뿐이다. 작은 표본의 smoke 검증과 다중 시드 밸런스 판정이 섞여 있다.
- 별도 근거: 코드와 현재 게임 기획은 일반 적 HP 성장률 15%다. 밸런스 보고서는 ‘3%로 확정’, 자동 합성 목표 55~70%라고 적혀 있다. 현재 하네스는 자동 합성 15% 이하, 전략 정책 15~40%를 기대한다. 보고서에는 현재 `strategic` 정책 설명도 빠져 있다.
- 수정 방향: 빠른 소수 시드 검증은 결정성·종료·상태 불변조건을 검사하고, 승률 구간 검증은 고정된 충분한 시드 집합을 사용하는 별도 모드로 분리한다. 합의된 현재 밸런스 목표에 맞춰 코드·하네스·보고서를 일치시킨다. 보고서에 맞추려고 HP를 임의로 3%로 되돌리지 않는다.
- 완료 조건: 기본 명령이 통과하고, `BALANCE_SEEDS=64 npm run test:balance` 결과를 실제 재측정하여 날짜·시드 생성 방식·정책·수치·목표와 함께 기록한다. 4시드 결과를 전체 승률 추정으로 쓰지 않는다.
- 추가 검증 보강: 하네스의 `ticks`는 전투에서만 증가한다. 카드 선택이 정체되면 `MAX_SECONDS`가 반복을 중단시키지 못하므로, 반복 횟수 또는 진행 감지 상한을 두고 phase/seed를 포함한 오류로 종료하도록 한다.

### R3 · 판정 정정 / 제품 규칙 확인 · 같은 틱 광역 적중은 현재 의도된 동작

- 위치: `src/game/simulation/projectile-system.ts`의 `advanceProjectiles`, `src/game/simulation/damage-resolution.ts:11`.
- 관찰: 모든 투사체의 충돌 목록을 먼저 계산한 뒤 피해를 순서대로 적용한다. 앞선 충돌에서 주 대상이 죽어도 이미 생성한 광역 impact는 주변 적에게 적용된다.
- 재현: 같은 위치에 적 A(HP 10), B(HP 100), A 대상 단일탄 피해 10과 광역탄 피해 30을 순서대로 도착시키면 A HP=0, B HP=70이다.
- **정정 근거:** `src/test/specification.test.ts:174`는 ‘같은 step에 도착한 아디나 범위 공격은 앞선 적중이 최초 대상을 처치해도 이미 생성된 범위 적중을 처리한다’를 명시적으로 검사한다. 따라서 초기 리뷰의 B HP=100 기대를 근거로 코드를 고치면 기존 계약을 깨뜨린다.
- 인계: 엔진은 유지한다. 게임 기획에 ‘이전 틱에 사망한 대상’과 ‘같은 틱에 이미 충돌 판정된 범위 공격’을 구별해 적으면 된다. 제품 의도가 변경될 때만 테스트·엔진·밸런스를 함께 바꾼다. 진단 테스트도 현재 B HP=70 정책을 보존하도록 정정했다.

### R4 · Medium · 상세 패널에서 새 규칙 카드의 사거리·공격 속도 효과가 누락된다

- 위치: `src/game/application/selectors/detail-selectors.ts:33` 및 34행.
- 원인: 실제 전투와 배치판 사거리 표시는 `run.activeRuleEffects`를 전달하지만 상세 패널은 `effectiveRange`와 `effectiveAps` 호출 시 빠뜨린다.
- 재현: 1성 리오에게 `rapid-cycle`, `extended-sensors` 규칙을 적용한다. 상세 ViewModel은 사거리 3.5, 초당 공격 1.35를 반환하지만 전투 계산은 각각 3.92, 1.5525다.
- 수정 방향: 두 함수에 동일한 activeRuleEffects를 전달한다. 수치 포맷은 표시 단계에서 처리한다.
- 완료 조건: 규칙 없음/각 규칙/레이더 또는 큐브 워치와 곱연산 조합에서 상세 값과 전투 계산이 일치한다. 레니 지원 탐색에도 해당 사거리 규칙을 적용할지는 카드 문구와 함께 별도 확인한다. 이 리뷰에서는 지원 사거리 의도를 확정하지 않았다.

### R5 · Medium · 카드 지급 라운드 진행 중 다음 카드 안내가 한 주기 앞선다

- 위치: `src/game/application/selectors/hud-selectors.ts:26`의 `nextCardRound`.
- 재현: `phase='combat'`에서 라운드 5→표시 10, 10→15, 30→35, 35→완료(undefined). 실제로는 현재 라운드 클리어 직후 카드를 받는다. 준비 단계에도 동일 문제가 있다.
- 원인: 아직 현재 라운드 카드를 받지 않았는데 `(round.number + 1)`을 기준으로 올림한다.
- 수정 방향: ready/combat에서 현재 라운드를 포함해 다음 지급 라운드를 계산한다. 카드 선택 중에는 현재 번호를 유지하며, 현재 MVP에 없는 40라운드 카드 지급은 추가하지 않는다.
- 완료 조건: 4/5/6, 9/10/11, 34/35/36/40라운드의 ready/combat/카드 선택/종료 상태를 확인한다. 특히 35라운드 전투 중 ‘완료’가 나오면 안 된다.

### R6 · Medium · 아이템 대상 선택 중에는 자동 장착까지 남은 시간이 보이지 않는다

- 위치: `src/ui/cards/CardSelectionOverlay.tsx`의 `itemTargeting` 분기, `src/game/application/commands/card-commands.ts`의 `tickCardSelection`.
- 근거: 제한 시간 표시는 카드 목록 분기 안에만 있다. 아이템 대상 선택 중에도 같은 타이머가 감소하며 만료되면 첫 미장착 실험체에게 자동 장착된다. 장착은 수동 교체·제거가 불가능하다.
- 재현 절차: 카드 선택 시간이 약 1초 남았을 때 아이템 적용을 눌러 대상 선택으로 진입한다. 대상 목록에서는 시간이 사라지지만 잠시 뒤 자동 장착된다. 별도 DOM 테스트에서 타이머 요소 부재를 재현했다. `mode=target&timer=1` 브라우저 fixture에서는 시간 표시 없이 대기한 뒤 현우에게 파워 모듈이 자동 장착되고 36라운드 ready로 전환되는 것까지 확인했다.
- 추가 경로: 오버레이를 닫아도 제한 시간은 흐르는데 `battleInfoViewModel`은 카드 타이머 대신 종료한 전투의 `round.remaining`을 보여준다. 일반 라운드 종료 후에는 `00:00`만 보이고 실제 선택 잔여 시간은 알 수 없다.
- 수정 방향: 타이머를 두 단계가 공유하는 영역에 표시하고, 만료 시 대상이 자동 선택됨을 대상 선택 화면에도 짧게 알린다. 대상 선택에 진입할 때 제한 시간을 임의로 초기화하지 않는다.
- 완료 조건: DOM 테스트에서 item-targeting에도 남은 시간이 보이고, 제한 시간 만료 후 대상 한 명에게만 장착되며 다음 준비 단계로 한 번만 전환되는지 검증한다.

## 아직 결함으로 확정하지 않은 사항

- 라운드 사이 준비 단계는 현재 구현 명세 상단에 의도된 MVP 동작으로 기록돼 있다. 과거 자동 다음 라운드 동작으로 복구하지 않는다.
- 히든 라운드와 정식 적 에셋은 후속 범위다. 미구현 자체를 이번 버그로 취급하지 않는다.
- 카드 고갈 시의 보상 정책, 레니 지원 사거리의 확장 감지 적용 범위, 적정 승률 목표는 제품 규칙을 명확히 해야 하는 부분이다.
- 스타일 파일 중복, 매 틱 렌더링 비용 등은 성능 측정 없이 장애로 단정하지 않았다.

## 확장 조사에서 추가 확인한 수정 항목

### R7 · Medium · 1280×720에서 상세 선택이 전체 화면 스크롤을 만든다

- 위치: `src/styles/layout.css`의 `.right-column`, `src/styles/panels.css`의 상세 패널 크기.
- 재현: 일반 게임에서 1280×720으로 열고 실험체를 복제한 뒤 선택한다. 레니 선택 시 DOM 문서 높이 737px, 상세 패널 bottom 737px, 복제 버튼 bottom 727px를 측정했다. 화면 높이는 720px다.
- 원인: `318px 1fr` 우측 grid와 상세 내용의 최소 크기가 화면보다 커진다. 상위 게임 화면은 고정 높이인데 내용 최소 높이와 overflow 정책을 조정하지 않았다.
- 영향: 화면 하단과 폐기 버튼을 보기 위해 스크롤해야 하고, 선택 전후 전장 높이도 바뀔 수 있다. `docs/design-guidelines.md`의 고정 게임 HUD 의도와 어긋난다.
- 수정: 우측 하단 행을 `minmax(0, 1fr)` 등으로 제한하고 상세 패널 내부에 필요한 스크롤을 준다. 내용만 숨겨 버튼을 접근 불가능하게 만들지 않는다. 318px 전투 정보 높이도 낮은 화면에서 조절한다.
- 완료 조건: 1280×720과 1366×768에서 미선택/아이템 장착/미장착/긴 이름 상태의 문서 overflow 없음, 모든 상세 조작에 접근 가능.

### R8 · Medium · 최소 지원 폭의 세로로 긴 화면에서 양옆 트랙이 잘린다

### R9 · Medium · 게임 밖에서 끌어온 데이터가 1번 슬롯 조작으로 해석된다

- 위치: `src/ui/battlefield/PlacementBoard.tsx`의 `onDrop`.
- 원인: `Number(event.dataTransfer.getData('slot'))`은 빈 문자열을 0으로 바꾼다. `Number.isInteger(0)`을 통과한다. 진행 중인 내부 drag가 있는지도 검사하지 않는다.
- 재현: 슬롯 1에 유닛을 둔 상태에서 슬롯 2의 drop 이벤트에 `getData: () => ''`를 전달하면 `onDrop(0, 1)`이 호출된다. 실제 DOM 이벤트 진단에서 확인했다. 외부 텍스트/이미지 드래그가 이 경로를 만들 수 있다.
- 영향: 원치 않는 이동·교환·합성까지 이어질 수 있으며, 합성 재료의 장착 아이템 소멸도 가능하다.
- 수정: 내부 전용 데이터 형식과 활성 dragSourceSlot을 함께 확인하고 빈 값/범위 밖 값을 거절한다. 파싱 후의 정수 검사만으로는 충분하지 않다.
- 완료 조건: 외부 문자열/이미지 drop과 빈 payload는 no-op, 유효 내부 move/merge/swap은 정상. 별도 진단 R9 실패가 통과로 바뀌어야 한다.

## 낮은 우선순위의 방어적 개선 — 현재 UI에서 발생한 장애와 구별

### H1 · 잘못된 슬롯 값이 state에 들어가면 다음 렌더가 예외를 던진다

`resolveBoardDrop`는 targetSlot의 정수/0..19 여부를 검사하지 않는다. 직접 `MOVE_OR_MERGE {sourceSlot:0,targetSlot:20}`을 주입하면 `boardViewModel`→`slotCenter`에서 undefined.x 예외가 난다. 정상 UI는 유효 슬롯만 생성하므로 원격 공격이나 일반 사용자 입력 취약점으로 부풀리지 않는다. reducer 경계에서 no-op/알림 처리하고 -1/20/NaN/소수 테스트를 추가하면 된다. 진단 H1이 이 조건을 검사한다.

### H2 · 같은 ready phase에서 RESET_RUN하면 drag 상태가 남는다

`useGameUiState`의 drag 초기화는 phase 변화에 의존한다. ready에서 dragSourceSlot=0을 둔 뒤 ready 초기 run으로 교체하면 0이 남는다. UI의 현재 새 런 버튼은 종료 phase에서만 보이므로 현행 주요 조작의 실패는 아니다. 즉시 재시작이나 개발용 reset을 추가하기 전에 run 식별자/명시적 reset으로 UI 상태도 초기화해야 한다. 진단 H2가 이를 검사한다.

### H3 · 결과 카드 목록이 카드 제목을 React key로 쓴다

`RunResultOverlay.tsx`는 `key={title}`인데 같은 아이템 카드를 여러 번 얻는 것은 정상이다. 현재 결과 목록은 정적이라 실제 유실/중복 렌더를 재현하지 않았지만 key 유일성 계약은 어긴다. 획득 순번 또는 record 식별자를 사용하고 같은 아이템 여러 장을 그대로 표시한다. 진단 fixture `mode=result`에 중복 아이템이 있다.

### H4 · TICK과 설정 값의 유효성은 호출자가 전부 책임진다

reducer에 NaN/음수/매우 큰 delta를 전달할 방어가 없고, spawnInterval=0이면 대기열을 한 틱에 모두 소비한다. 현재 useGameLoop는 항상 1/60을 보내므로 실제 UI 장애로 단정하지 않는다. 저장/재생/개발 콘솔 API를 붙일 때 유한 값·범위 검증을 boundary에 추가한다. 모든 내부 함수에 방어 코드를 반복할 필요는 없다.

## 밸런스 확장 측정 결과

현재 코드 그대로 실행한 64시드 결과다. 시드는 `Math.imul(index + 1, 0x9e3779b9) >>> 0`, 각 정책 같은 64개 집합이며 패키지 기본 step을 사용했다.

| 정책 | 승리 | 오버플로 | 타임아웃 | 평균 도달 라운드 | 승리 런 평균 전투 시간 |
| --- | ---: | ---: | ---: | ---: | ---: |
| initial-four-only | 0/64 | 11 | 53 | 11.0 | 해당 없음 |
| auto-spend | 0/64 | 64 | 0 | 23.4 | 해당 없음 |
| auto-merge | 0/64 | 61 | 3 | 27.2 | 해당 없음 |
| auto-merge-first-card | 0/64 | 64 | 0 | 25.2 | 해당 없음 |
| strategic | 21/64 | 43 | 0 | 37.7 | 1,173초 |

- 기존 보고서의 3% 체력 성장/auto-merge 67%는 현재 기준이 아니다. 현재 값은 15%/0%다.
- 현재 하네스 목표는 통과하지만 ‘합성을 바로 할수록 좋아진다’는 목표를 입증하지는 않는다. strategic은 공간 부족 시 합성과 라운드 준비 배치를 결합한 다른 정책이다.
- strategic의 레니 초기 1명 군은 14/29승, 2명 군은 1/10승이다. 차이는 약 38%p지만 작은 표본과 다른 조합의 혼입 때문에 레니 2명 자체가 원인이라고 단정하지 않는다. 역할별 대조 정책/더 큰 동일 시드 집합으로 확인해야 한다.
- 카드 선택군 승률은 카드 인과 효과가 아니다. 높은 우선순위 카드가 많이 뽑히고 오래 살아남은 런이 카드를 더 얻는 편향이 있다. 레이더는 strategic 64런에서 한 번도 선택되지 않아 현재 데이터로 효과를 평가할 수 없다.
- 하네스의 seconds는 전투 틱만 센다. 준비·카드 읽기·장착 조작이 빠져 있어 실제 플레이 20~35분의 직접 증거가 아니다.

## 재현 도구와 실행 방법

추가 런타임 의존성이나 게임 코드 수정 없이 기존 Vitest/React를 재사용했다. 일반 테스트 자동 탐색을 피하려고 진단 파일을 `*.test.*`로 이름 짓지 않았다.

```sh
# 일반 회귀 검사: 기존 59개가 그대로 통과해야 함
npm test
npm run build

# 별도 리뷰 진단: 미수정 상태에서 실패하는 것이 예상 결과
./node_modules/.bin/vitest run --config docs/review/vitest.config.ts

# 특정 문제만 재현
./node_modules/.bin/vitest run --config docs/review/vitest.config.ts -t 'R9'

# 현재 밸런스: 기본 4시드는 실패, 64시드는 통과
npm run test:balance
BALANCE_SEEDS=64 npm run test:balance
```

진단 파일: `docs/review/system-probes.tsx`. R1 정책(빈 풀 안전 탈출), R4/R5/R6/R9/R10 결함과 H1/H2 방어 조건이 기대 동작을 assert하므로 현재 실패한다. 나머지는 현재 계약을 보호하거나 관찰 사실을 기록한다. 이 진단을 통째로 녹색으로 만들기 위해 H/D 항목까지 무조건 구현하지 않는다. 실제 수정 항목의 테스트를 기존 `src/test`로 옮길 때 근거와 ID를 유지한다.

보존한 증거는 `docs/review/results.json`(진단별 실제 결과, 실행 버전, src TS/TSX/CSS 100개 파일의 결합 SHA256)과 `docs/review/balance-64.log`(64시드 명령 전체 출력)다. 이 fingerprint는 검토 시점 식별용이며 100개 파일 모두에 동적 테스트가 있다는 뜻이 아니다.

브라우저 fixture는 `npm run dev` 후 출력된 호스트의 `/docs/review/ui-fixture.html`로 연다. 쿼리는 `mode=cards`, `mode=target`, `mode=result`, `mode=empty`; `&timer=1`을 붙이면 실제 useGameLoop가 작동한다. 기본은 화면 조사 중 임의 시간 초과를 막기 위해 멈춘다. **실제 GameScreen/명령 처리 코드를 사용하지만 준비한 state를 주입하므로 전체 런을 재현한 증거는 아니다.** `dist`의 제품 진입점에는 포함되지 않는다.

## 검토 범위와 남은 한계

- 핵심 source: application 명령/reducer/selectors, domain 모델·규칙, simulation 전체 system·skill, config·RNG, React provider/loop/UI hooks, 현재 사용 UI·CSS를 검토했다.
- 주변 source: package/TS/Vite 설정, 에셋 생성 Python, 현재 기획/보관 명세/밸런스·과거 감사 문서를 대조했다.
- 정적 검토로 확정할 수 없는 실제 유저 학습성, 장시간 프레임 저하, 외부 배포 환경은 별도 검증 과제다. 네트워크 서비스·계정·백엔드는 현재 제품에 없어 불필요한 서버 보안 과제를 추가하지 않았다.
- 과거 감사의 ‘자동 복제 100% 승리’, ‘10라운드 알파 최종 승리’, ‘약한 옛 성급 배율’, ‘00:60 표시’는 현재 상태에 그대로 적용하지 않았다.
- 요구사항이 불명확한 지원 소스 소멸/같은 틱 판정/RNG 정책을 임의 버그로 늘리지 않았다. 현재 계약을 유지하는 부분은 수정하지 않는다.
